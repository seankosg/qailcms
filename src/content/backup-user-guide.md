# QAIL CMS 백업 & 복원 사용자 가이드

> 이 문서는 IT 지식이 없는 일반 사용자도 스스로 백업 상태를 확인하고, 필요할 때 복원까지 완수할 수 있도록 작성되었습니다. 어려운 용어는 괄호 안에 정식 명칭을 병기합니다.

---

## 1. 이 시스템은 무엇인가요?

- **백업(Backup)** 은 "지금 이 순간의 앱 전체 데이터를 안전한 금고에 넣어두는 것" 입니다.
- **복원(Restore)** 은 "금고에 넣어둔 특정 시점의 데이터를 다시 꺼내, 앱을 그때 상태로 되돌리는 것" 입니다.
- 언제 필요할까요?
  - 실수로 대량의 행을 삭제했을 때
  - 잘못된 엑셀 파일을 임포트하여 데이터가 오염되었을 때
  - 특정 시점의 데이터가 감사(Audit) 목적으로 필요할 때
  - 시스템 이관/이전 준비 시

---

## 2. 한눈에 보는 구조

```
  [ 앱 데이터 (Database + Storage + 사용자 계정) ]
                  │
                  │  ① 매일 도하 시간 23:50 자동 실행
                  ▼
     [ 스냅샷(Snapshot) 생성 → 무결성 검증(SHA-256) ]
                  │
                  ▼
  [ 안전한 저장소 (Storage bucket: db-backups) ]
                  │
                  │  ② 필요할 때 관리자가 선택
                  ▼
          [ 복원(Restore) 실행 ]
                  │
                  ▼
  [ 앱이 선택한 스냅샷 시점으로 되돌아감 ]
```

- 백업 파일은 zip 형태로 저장되며, 관리자는 **로컬 컴퓨터로 다운로드**하여 회사 보관 정책에 맞게 보존할 수 있습니다.

---

## 3. 백업의 구성 요소 (쉬운 설명)

| 요소 | 쉬운 설명 | 정식 용어 |
| --- | --- | --- |
| 스냅샷 | 앱 전체의 "특정 시점 사진" | Snapshot |
| 자동 백업 | 매일 정해진 시간에 사람 손 없이 만들어지는 백업 | Scheduled Backup |
| 수동 백업 | 사용자가 원할 때 즉시 만드는 백업 | On-demand Backup |
| 임포트 전 안전 백업 | 대량 임포트 직전 자동으로 만들어지는 임시 백업 | Pre-import Safety Snapshot |
| 저장 위치 | 백업이 실제 저장되는 안전한 창고 | Storage bucket `db-backups` |
| 보관 기간 | 오래된 백업을 언제까지 두고 언제 지울지 정한 규칙 | Retention Policy |
| 무결성 검증 | 백업 파일이 도중에 손상되지 않았는지 확인하는 도장 | SHA-256 Checksum |

---

## 4. 자동 백업은 언제 실행되나요?

- **기본값**: 매일 **카타르 시간(AST, UTC+3) 23:50** 실행.
- 실행 시각/요일 변경 방법:
  1. `/admin/backup` 페이지 접속
  2. **Schedule** 카드의 "Edit schedule" 버튼 클릭
  3. 요일 체크박스, 시각(HH:mm), 시간대(Asia/Qatar 기본) 조정 후 **Save**
- **실패 또는 지연되었을 때**:
  - 최근 성공한 자동 백업이 26시간을 초과하면 상단에 붉은 **Overdue** 배지가 표시됩니다.
  - 이 경우 곧바로 아래 **5. 수동으로 백업 만들기** 를 실행하십시오.

---

## 5. 수동으로 백업 만들기 (3-Step)

1. `/admin/backup` 진입 → 상단 **Create Snapshot** 카드 열기
2. 백업 이유를 짧게 메모 입력 (예: "임포트 전 안전 백업", "월말 정산 완료 후")
3. **Save Current Data** 버튼 클릭 → 진행률 바가 100% 될 때까지 대기

> 진행률이 100%가 되면 하단 **Snapshot List** 최상단에 새 항목이 등장합니다.

---

## 6. 알림 설정

- **Notifications** 카드에서 다음을 각각 켜고 끌 수 있습니다.
  - 성공 알림 (Success)
  - 경고 알림 (Warning: 지연/느림)
  - 실패 알림 (Failure)
- Slack, Teams 같은 외부 도구로도 알림을 받고 싶다면 **Webhook URL** 을 입력하십시오. 붙여넣은 URL은 저장 즉시 테스트 신호를 보냅니다.

---

## 7. 로컬(내 컴퓨터)에 백업 파일 내려받기

1. **Snapshot List** 에서 원하는 스냅샷의 우측 **⋯ 메뉴 → Download .zip** 클릭
2. 저장된 zip 파일을 열면 다음과 같은 구조가 보입니다.

```
snapshot_20260720_2350.zip
├── manifest.json          ← 스냅샷 정보 요약 (버전, 시각, 행 수)
├── hash.json              ← 무결성 검증용 체크섬
├── auth_users.json        ← 사용자 계정 백업
├── storage/               ← 첨부 파일/이미지 백업
└── tables/
    ├── abd_items_raw__part_001.json
    ├── defect_items_raw__part_001.json
    ├── task_management_raw__part_001.json
    └── ...
```

> **보관 팁**: 회사 규정상 "외부 저장이 금지된 데이터" 라면 반드시 내부 파일 서버 지정 폴더에만 저장하세요. USB/개인 클라우드 저장 금지.

## 8. 복원(Restore) — 가장 중요한 챕터

> ⚠️ **경고**
> - 복원은 **관리자(admin) 계정만** 실행할 수 있습니다.
> - 실행 즉시 **현재 데이터가 스냅샷 시점의 데이터로 대체** 됩니다.
> - 진행 도중 사용자들이 편집한 데이터는 사라질 수 있으므로, 실행 전 공지하십시오.

### A. 전체 복원 절차 (6-Step)

1. `/admin/backup` 진입
2. 되돌리고 싶은 스냅샷의 **Restore** 버튼 클릭
3. **"Create pre-restore safety backup"** 옵션은 반드시 **체크 상태 유지** (권장)
4. 확인 다이얼로그에 표시된 문구 `RESTORE <스냅샷명>` 을 그대로 입력
5. **Run** 클릭
6. 하단 **Restore Run Log** 에서 실시간 진행 상황과 최종 결과 확인

### B. 선택 복원(Selective Restore)

- 특정 테이블만 되돌리고 싶을 때(예: SM 데이터만 이상함) 사용합니다.
- Restore 다이얼로그 안의 **Select tables to restore** 목록에서 원하는 항목만 체크하십시오.
- ⚠️ 마스터 테이블(팀, 사용자, 시스템 마스터 등)은 대체로 **함께 복원**하는 것을 권장합니다. 관련 참조 관계가 어긋날 수 있기 때문입니다.

### C. 사용자 계정(auth users) 복원

- **Include auth users** 체크 시 백업 시점의 계정/역할이 그대로 복구됩니다.
- 신규 가입한 사용자가 있는 경우, 복원 후 해당 사용자는 재가입이 필요할 수 있습니다.

### D. 파일(Storage) 복원은 백그라운드로 이어집니다

- 첨부 파일이 많은 경우 DB 복원 완료 후에도 파일 복원은 몇 분간 진행됩니다.
- 진행률은 **Restore Run Log** 하단 **Storage progress** 표시에서 확인 가능합니다.

### E. 복원 후 반드시 확인할 3가지

1. **행 수 대조**: Dashboard 상단 카운트가 예상 값과 일치하는지
2. **무결성 리포트**: Restore Run Log 마지막 줄에 `integrity: OK` 표시 확인
3. **도출 컬럼 재계산 완료 여부**: SM/TM 의 Status 컬럼, Progress 계산이 정상 표시되는지 (필요 시 관리자가 "Recompute" 버튼 실행)

## 9. 상황별 대응 시나리오 (Playbook)

### 시나리오 A. "방금 잘못된 파일을 임포트했어요"

1. 즉시 `/admin/backup` 접속
2. 임포트 직전에 자동 생성된 **`pre-import-*` 스냅샷** 을 찾습니다.
3. 해당 스냅샷의 **Restore** 실행 → 관련 테이블만 선택 복원 가능

### 시나리오 B. "누군가 특정 테이블의 행을 대량 삭제했어요"

1. 삭제 이전 시각의 스냅샷 선택
2. **Select tables to restore** 에서 해당 테이블만 체크
3. Restore 실행 후 행 수 확인

### 시나리오 C. "어제 저녁 이전 상태로 되돌리고 싶어요"

1. Snapshot List 를 날짜 내림차순 정렬
2. 어제 23:50 자동 백업 선택 → 전체 복원

### 시나리오 D. "감사용으로 특정 시점 데이터를 뽑고 싶어요 (복원은 원치 않음)"

1. 해당 시점 스냅샷의 **Download .zip** 만 실행
2. zip 내부 `tables/*.json` 을 감사 담당자에게 전달 (복원 X)

## 10. 보관 정책(Retention)

- **keep_last_n**: 최근 N개는 무조건 보존
- **keep_days**: N일이 지난 것은 자동 삭제
- 두 규칙 중 하나라도 만족하면 보존됩니다. (안전 우선)
- 특정 스냅샷을 **영구 보존** 하려면 그 항목의 🔒 **Lock 아이콘** 클릭 → 자동 삭제 대상에서 제외됩니다.

## 11. 문제 해결 (FAQ)

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| Download 버튼이 회색이에요 | 다운로드 권한이 없는 계정 | Admin 계정으로 로그인 필요 |
| Restore 버튼이 안 보여요 | Admin 이 아닌 계정 | Admin 계정으로 로그인 필요 |
| 상단 **Overdue** 배지 | 26시간 이상 자동 백업 성공 없음 | **5. 수동 백업** 즉시 실행 후 원인 확인 |
| 스냅샷 옆 **integrity: FAIL** | 저장 도중 손상 가능성 | 해당 스냅샷은 사용 금지, 새 백업 실행 |
| Restore 도중 실패 로그 | 저장소 일시 오류 | Restore Run Log 확인 후 재시도, 반복되면 관리자 문의 |

## 12. 용어 사전

- **스냅샷(Snapshot)**: 특정 시점의 앱 전체 데이터 사진.
- **Manifest**: 스냅샷의 목차. 어떤 테이블이 몇 행 담겼는지 기록.
- **SHA-256**: 파일 손상 여부를 확인하는 지문(체크섬).
- **Retention**: 얼마나 오래 보관할지 정한 규칙.
- **RLS (Row Level Security)**: 사용자가 볼 수 있는 행을 데이터베이스가 직접 통제하는 보안 규칙.
- **auth users**: 로그인 계정 정보(이메일, 역할).
- **Storage bucket**: 파일이 저장되는 논리적 창고.

---

## 13. 책임과 한계

- 자동 백업 사이의 시간(예: 23:50 이후 다음 날 아침) 동안 발생한 데이터 변경은 손실될 수 있습니다. 중요한 대량 변경 전에는 **수동 백업**을 실행하십시오.
- `auth`, `storage`, `vault` 시스템 스키마는 앱이 직접 수정할 수 없으므로 별도의 안전 규칙에 따라 처리됩니다.
- 백업/복원은 강력한 관리 도구입니다. 실행 전 반드시 이 문서의 절차를 따르십시오.
